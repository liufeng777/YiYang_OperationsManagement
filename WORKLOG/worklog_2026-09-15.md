# 工作日志 2026-09-15

## 任务1：修复「登录后切换页面被踢回登录页」并接入真实登录

### 任务描述

- 用户反馈：login 接口未实现，先存了假 token（`mock-token-${Date.now()}`），但切换页面时会跳转回登录页，询问原因。
- 涉及文件：`src/store/modules/user.ts`、`src/router/guard.tsx`（AuthGuard），以及请求层的 401 处理。

### 根因分析（已用后端实测确认）

请求链路：
1. 登录后 store 写入假 token `mock-token-xxx`；
2. `src/utils/request.ts` 请求拦截器**无条件**把它塞进请求头 `Authorization: Bearer mock-token-xxx`；
3. 后端对「携带了 Authorization 但 token 无效」的请求返回 **HTTP 401 / code=1003「token 无效」**；
4. 响应拦截器命中 401 → `useUserStore.getState().logout()` 清空 token + `window.location.href = '/login'`；
5. 首页 dashboard 为纯 mock（不发请求）所以看起来正常；一旦切换到已接入真实接口的页面（机构/服务/活动等），页面挂载即发请求 → 401 → 被踢回登录页。

实测对照（决定性证据）：

| 请求 | 后端响应 |
| --- | --- |
| 不带 `Authorization` 头 | HTTP **200**，`code=0` 正常返回 |
| 带 `Authorization: Bearer mock-token-xxx` | HTTP **401**，`code=1003`「token 无效」 |

即后端是「有 token 就校验，无效就拒」，因此假 token 反而把请求搞挂了。

**额外发现**：登录接口**其实已经实现且可用** —— `POST /api/v1/admin/auth/login` + `{username:"admin", password:"123456"}` 返回 200 与真实 JWT（`expire_in: 7200`），携带该 token 请求 profile、机构、服务、活动、服务分类、耗材等接口均为 200。用户此前以为未实现。

### 解决方案

用户决策：**直接接入真实登录接口**（而非保留假 token）。

- **`src/store/modules/user.ts`**：`login` 启用 `authApi.login`，用返回的 `token` 与 `admin` 映射 `UserInfo`；对后端未返回的字段做兜底（`avatar_url→avatar`、`phone/email ?? null`、`roles ?? []`、`permissions ?? []`）。
- **`src/api/modules/auth.ts`**：按后端实测校准契约 —— `LoginResult.expire_in`（原写作 `expires_in`）；`AdminProfile` 将 `avatar_url / phone / email / last_login_at / last_login_ip / permissions` 改为可选（登录出参仅返回 `id/username/nickname/roles`）。
- **`src/utils/request.ts`**：不再需要「按前缀跳过 Authorization」的临时绕过，统一携带真实 token（当前文件已回到统一逻辑，无 mock 分支残留）。

### 附带修复：ServicesTab 与新契约不匹配（既有编译错误）

发现 `institution.ts` 已改为「批量关联」模型（新增 `batchCreateInstitutionService`、删除 `InstitutionServiceDTO`），但 `ServicesTab.tsx` 仍用旧类型，导致多处类型错误（用户确认一并修复）。

- **`src/api/modules/institution.ts`**：
  - 新增 `InstitutionServiceRow`（关联记录 + 平铺 `service_name` / `service_category_name` / `is_home_service` / `price_override` / `status` / `sort` / `remark`）与 `InstitutionServicePage`；

  - 恢复 `updateInstitutionServiceStatus`（契约中一度注释，但后端实测仍可用，页面上下架依赖它）。

实测校准要点：

## 任务2：机构详情 Tab 角标展示「已关联服务数量」

### 任务描述

- 用户需求：打开机构详情时就需要获取机构服务（数量），因为 Tab 标题后面需要展示已经关联的服务个数。
- 现状：数量仅由 `ServicesTab` 渲染后经 `onCountChange` 回传，默认停在「基础资料」Tab 时角标取不到值（初始 0），需切到服务 Tab 才有数字。

### 解决方案

- **`src/pages/institution/detail/index.tsx`**：
  - 新增 `fetchServiceCount`：打开详情即调用 `getInstitutionServiceList(id, { page: 1, page_size: 1 })`，取分页 `total` 作为已关联服务数量（只取总数、不拉全量，开销极小，与 ServicesTab 的全量拉取不重复）；
  - `serviceCount` 类型改为 `number | null`：未取到时 Tab 只显示标签，避免先闪出「服务项目 0」；
  - 保留 `ServicesTab` 的 `onCountChange`：切换到服务 Tab 或增删服务后，用其回传的准确数量覆盖角标。
