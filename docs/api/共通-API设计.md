# 幸福颐养平台 - 共通API 设计

> **本文件为全平台统一「共通层」定义**。运营后台、用户端、医护服务小程序、协同工作台、数据大屏 5 端 API 文档均引用本文件，避免重复定义与口径冲突。
>
> 各端文档中的响应结构、分页、鉴权、时间/金额格式、状态枚举、错误码等通用内容，统一以本文件为准；端侧仅保留**本端特有**约定与业务接口。

## 文档信息

- **版本**: v1.1
- **状态**: 已定稿
- **关联**: 数据库设计 v1.10；各端 API 设计均引用本文件
- **v1.1（2026-08-23）**: 新增 §1.4「出参子结构准则」——列表平铺、详情聚合、一对多必嵌套，多对一关联展示用 `xxx_id+xxx_name` 平铺字段；各端已按此拉齐（用户端/运营后台端/医护端工单订单关联名称已平铺）。

## 1. 响应结构（统一）

### 1.1 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

- `code`：`0` 表示成功；非 0 为业务/系统错误码（见 §4 错误码）。
- `message`：提示信息，成功为 `ok`，失败为可展示的错误说明。
- `data`：业务数据；**列表接口固定为** `{list, total, page, page_size}`（见 §2 分页）。

### 1.2 列表成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [ { } ],
    "total": 25,
    "page": 2,
    "page_size": 10
  }
}
```

### 1.3 业务错误响应

```json
{
  "code": 4001,
  "message": "参数错误",
  "data": null
}
```

> 字段校验错误（入参级）可在 `data` 返回 `[{field, message}]` 形式逐条说明（见 §4.2 字段级错误）。

### 1.4 出参子结构准则（统一）

> 全局统一「列表平铺、详情聚合、一对多必嵌套」的组装约定。服务端在 **DAO 层 join 出扁平行后，由 Service/组装器装配为 DTO** 再返回，禁止把 join 原始行直接透传。**各端出参一律遵守本小节，端内不再另定。**

1. **一对多（1:N）子记录 → 必用嵌套数组** `[ {...} ]`
   工单的 `service_records`、订单的 `items`/`consumables`、留痕的 `vital_signs_*_detail`、病例的 `medical_records` 等一对多明细天然为数组内嵌对象。**禁止**拍平成 `item_0_x/item_1_x` 平铺列。
2. **多对一（N:1）关联展示 → 用平铺冗余字段** `xxx_id` + `xxx_name`（必要时 `xxx_phone`）
   如 `member_id`+`member_name`、`staff_id`+`staff_name`、`service_id`+`service_name`、`inst_id`+`inst_name`。列表页与详情页（常规场景）均平铺，避免前端循环拆对象、减少 JS 对象判断。
   - **例外（允许对象嵌套）**：仅当该关联是一组**强内聚的完整子实体**、且前端必整体消费时，才用 `"xxx":{...}`，如健康预警 `warning:{...}`（含处置人姓名/时间等多字段聚合快照）。
3. **聚合/统计接口（大屏、运营看板）**：出参为聚合对象/数组，按各端接口自述，不受 §1.1/§2 分页包装约束（见 §2）。
4. **字段命名**：平铺关联名统一 `{实体}_id` / `{实体}_name`；嵌套对象内字段保留其在 DAO DTO 中的原始命名，不重复加前缀。

## 2. 分页规范

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| page | int | N | 页码，默认 1 |
| page_size | int | N | 每页条数，默认 10，最大 100 |
| keyword | string | N | 模糊搜索关键字（按各接口字段说明） |

- 列表接口分页入参为通用约定，**各端各接口不再重复列出**。
- 分页响应结构 `{list, total, page, page_size}`，为列表接口唯一契约。

> 数据大屏接口 `data` 为聚合对象/数组，**不适用**分页包装，按大屏特有约定。

## 3. 鉴权与请求头

### 3.1 通用请求头

```http
Content-Type: application/json
Authorization: Bearer ***
X-Request-ID: <UUID>          // 链路追踪，可选
X-Client-Type: web-admin      // 客户端类型标识
```

### 3.2 Token 颁发与来源

- 各端独立登录、基于各自账号签发 token：运营后台/协同/数据大屏 → `admins`；用户端 → `users`（经 `user_member_relations` 关联当前操作会员 `members`）；医护小程序 → `institution_staff`（`staff_type=2`）。
- 所有返回中的手机号、证件号须**脱敏**展示；健康/定位数据仅在授权范围返回。

### 3.3 数据权限

- 平台层统一控制：JWT 内含 `institution_id` 与 `data_scope`（`self`/`all`）。
- 机构范围数据按 JWT `institution_id` + `data_scope` 过滤；跨机构/全量仅平台运营可见。
- 各端接口标注的权限码（`permissions.code` / `permission.code`）为授权判定基础。

## 4. 错误码（全局统一）

### 4.1 错误码段

| 码段 | 含义 | 归类 |
|------|------|------|
| 0 | 成功 | 通用 |
| 1000-1999 | 参数、认证、权限等通用错误 | 通用 |
| 2000-2999 | 会员/账号相关 | 业务域 |
| 3000-3999 | 健康档案/评估/方案相关 | 业务域 |
| 4000-4999 | 服务、耗材、订单、结算相关 | 业务域 |
| 5000-5999 | 工单、排单、派单、上门执行相关 | 业务域 |
| 6000-6999 | 活动、咨询、随访、预警相关 | 业务域 |
| 7000-7999 | 预约、消息、CMS、运营相关 | 业务域 |

### 4.2 通用错误码（各端一致）

| code | 说明 |
|------|------|
| 400 | 参数校验失败（字段错误，配合 `data:[{field,message}]`） |
| 401 | 未登录 / token 失效 |
| 403 | 无权限（权限码不满足或超出机构数据范围） |
| 404 | 资源不存在 |
| 429 | 请求过频（触发限流） |
| 500 | 服务内部错误 |
| 600 | 业务冲突（如排班重复、工单状态不允许流转） |

> 历史版本出现的 `4001/4010/4030/5000/6001/6002` 等编码在新接口中**已统一收敛为**上述 `400/401/403/500/600` 短码；具体到各端文档时一律引用本表，不再各自定义。

### 4.3 字段级错误

```json
{
  "code": 400,
  "message": "参数错误",
  "data": {
    "errors": [
      { "field": "phone", "message": "手机号格式不正确" },
      { "field": "amount", "message": "金额必须大于0" }
    ]
  }
}
```

## 5. 时间戳与金额格式（通用）

| 项 | 约定 |
|----|------|
| 时间戳 | 所有存储/接口时间字段为 **UTC 秒数（BIGINT）** |
| 日期字段 | 如 `service_date`/`schedule_date`/`appointment_date` 使用 `yyyy-MM-dd`；趋势 `date` 用 `yyyy-MM-dd`、`month` 用 `yyyy-MM` |
| 入参时间 | 接受 `yyyy-MM-dd HH:mm:ss` 或 UTC 秒数时间戳，内部统一转 UTC 秒存储 |
| 金额 | 统一 `DECIMAL(10,2)`（JSON 数字），单位元 |

## 6. 状态枚举字典（全局唯一权威口径）

> 以下枚举为**唯一权威定义**。各端涉及的名词一律引用此表，端内不再重复定义（若端内有差异需以本表为准回改）。

### 6.1 订单 `service_orders.order_status`

| 值 | 说明 |
|----|------|
| 1 | 待支付 |
| 2 | 待确认（用户已完成支付，等待医护/机构确认安排） |
| 3 | 生效中（已确认，工单执行中） |
| 4 | 已完成（全部工单完成） |
| 5 | 已取消 |
| 6 | 已退款 |

**正向流转：** `1 待支付` →（支付成功）→ `2 待确认` →（医护/机构确认，写 `confirmed_at/confirmed_by`）→ `3 生效中` →（全部工单完成）→ `4 已完成`。
**逆向/终止：** 支付前取消：`1→5`；支付后在 `2 待确认 / 3 生效中（未开始）` 可申请取消，已支付则生成退款，退款完成 → `6 已退款`。各端确认/取消动作由协同端（`POST /api/v1/staff/orders/:id/confirm`）与运营后台（`POST /api/admin/orders/:id/confirm`）执行。

## 7. 上传契约（通用）

- 照片/视频/文件上传走对象存储（OSS）：先上传得到 **URL**，再随业务接口提交。
- 上传统一走 `POST /upload`：

| 接口 | 方法 | 说明 |
|------|------|------|
| 文件上传 | POST `/upload` | `multipart/form-data`，字段 `file`，授权登录态 |
| 删除文件 | DELETE `/upload/:key` | 软删除 OSS 对象（可选） |

**上传成功出参 data：**

```json
{
  "url": "https://oss.xxx/xxx/yyy.jpg",
  "key": "xxx/yyy.jpg",
  "size": 102400,
  "mime_type": "image/jpeg"
}
```

- 弱网/断网：客户端本地暂存，联网后重传（幂等：携带 `client_trace_id`，服务端去重）。
- 签到/留痕照片 URL 为证据链必要字段（已完成工单无签退打卡；见医护端 §4）。

## 8. 批量操作契约（通用）

> 适用于运营后台各类 `batch-*` 批量接口（批量上下架、批量派单、批量打标签、批量推送等）。

- 统一路径：`POST /batch-*`。
- 统一入参 body：`{ ids: [...], ...操作可选字段 }`。
- 服务端事务内逐条校验（软删引用 / 状态机 / 机构数据范围 / 权限码）。
- 写操作逐条留痕。
- 统一出参：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "success_count": 8,
    "fail_count": 2,
    "fail_list": [
      { "id": 5, "reason": "机构范围不符" },
      { "id": 9, "reason": "状态不允许操作" }
    ]
  }
}
```
